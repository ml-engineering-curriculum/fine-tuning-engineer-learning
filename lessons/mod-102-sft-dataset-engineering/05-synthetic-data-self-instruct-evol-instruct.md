# Synthetic Instruction Data: Self-Instruct and Evol-Instruct

**Estimated read:** 45 minutes.
**You should be able to, by the end:** describe the Self-Instruct bootstrapping loop and Evol-Instruct's evolution operators, wire quality filters and provenance metadata into either pipeline, and name the licensing questions that must be resolved *before* you run a synthetic generation against a proprietary teacher.

## Why synthetic data at all

Human-authored SFT data is expensive. High-quality instruction–response pairs on a specific domain typically run several dollars per pair once you include reviewer time. If your goal is a 100k-example fine-tune covering reasoning, code, safety refusals, tool calls, and persona work, human authoring alone is intractable for most teams.

Synthetic instruction data — generated by a stronger model, filtered, and formatted — closes the gap. The tradeoff is that the output is a distillation of the teacher, including its biases, its refusal patterns, its formatting tics, and its licensing terms. Chapter 7 covers the licensing side; this chapter covers the pipeline.

## Self-Instruct: the bootstrapping loop

**Wang et al. (2023) — "Self-Instruct: Aligning Language Models with Self-Generated Instructions"** introduced the recipe that essentially every subsequent open synthetic instruction dataset is built on. The version they ran used GPT-3 as the teacher; the pattern generalizes.

The loop:

1. **Seed set.** Start with 175 hand-authored instruction–instance pairs across diverse tasks (their number; you can vary it). The seeds are the anchor for topic diversity — the pipeline will inherit their coverage bias.
2. **Instruction generation.** Sample 6 seed instructions (in the paper: 8 total — 6 human, 2 model-generated as the pool fills) and prompt the teacher: "Come up with a new task similar in style but different in content." Parse the response for a new instruction.
3. **Task-type classification.** Ask the teacher whether the new instruction is a classification task or an open-ended generation task. This affects step 4.
4. **Instance generation.**
   - For open-ended tasks: prompt the teacher for an input–output pair.
   - For classification tasks: prompt for an *output-first* generation (asking for the class label first, then a corresponding input), to counter the model's tendency to always pick the same class.
5. **Filtering.**
   - **ROUGE-L overlap** against every instruction already in the pool: keep only if `ROUGE-L < 0.7` against the closest existing instruction.
   - **Heuristics**: drop if the instruction contains keywords the model tends to fail on (image, graph), is too long or too short, starts with `Write a program`, etc.
   - **Uniqueness**: exact-match dedup on instructions.
6. **Repeat.** Add surviving items to the pool. Loop until you have the target size.

The paper generated 52k instructions from 175 seeds. Alpaca (Taori et al., 2023) is essentially Self-Instruct at 52k with `text-davinci-003` as the teacher and lighter filtering.

### What Self-Instruct gets right

- **Diversity via seed variety.** With enough seeds spanning task types, the pipeline covers more ground than a naïve "generate 50k similar prompts" call.
- **The output-first trick for classification.** Small idea, large effect on class balance.
- **ROUGE-L dedup during generation, not just at the end.** Prevents drift into local generation loops.

### What Self-Instruct gets wrong (or leaves for you)

- **Bland responses.** The teacher's default answers are the shortest correct thing; you often want longer, more thorough responses for SFT.
- **Difficulty distribution.** All prompts end up roughly the same difficulty, because the teacher generates from its own comfortable middle. Hard prompts get under-represented.
- **Correctness at scale.** No pass verifies that the teacher's response is *right*. On math and code, expect 15–30% error rates in the raw generations (the exact number is task-dependent; measure yours).

Evol-Instruct addresses the difficulty distribution and, indirectly, the response-quality issues.

## Evol-Instruct: mutating instructions to make them harder

**Xu et al. (2023) — "WizardLM: Empowering Large Language Models to Follow Complex Instructions"** introduced Evol-Instruct as the recipe behind the WizardLM family. Where Self-Instruct generates instructions from seeds, Evol-Instruct **mutates existing instructions** using explicit evolution operators to increase depth or breadth.

The operators, from the paper:

**Depth evolutions** (make the existing prompt harder):

- **Add constraints.** "…but do not use recursion."
- **Deepen.** Turn a shallow question into one requiring multi-step reasoning.
- **Concretize.** Replace generic language with specific instances.
- **Increase reasoning steps.** Force multi-hop rather than direct.
- **Complicate input.** Add irrelevant or misleading context.

**Breadth evolutions** (produce a topically-related but distinct prompt):

- **Mutation** to a related domain, adjacent task, or novel scenario built on the same skill.

The loop:

1. Start from a seed instruction pool (from Self-Instruct, Alpaca, or hand-authored).
2. Randomly select an instruction and an evolution operator.
3. Prompt the teacher with the operator's template: "Rewrite this instruction to be harder by adding one constraint that is difficult to satisfy…"
4. Filter the result:
   - **Not-evolved check**: teacher explicitly says "this cannot be made harder" or the output is trivially the same.
   - **Difficulty check**: is the new instruction actually harder? A common signal is response length or presence of reasoning cues.
   - **Coherence check**: does the mutated instruction still make sense?
5. Add survivors to the pool and re-generate the response with the teacher.
6. Iterate multiple rounds ("evolutions"). WizardLM used ~4 rounds.

The end effect is a dataset skewed toward harder-than-seed instructions with responses long enough to fine-tune coherent multi-step behavior.

### Evol-Instruct caveats

- **Difficulty drift.** After enough rounds, instructions become artificially convoluted — "Write a Python function that computes X, but do not use recursion, or any loop, or any built-in library, and explain each step in Latin." These over-constrained prompts are training data for over-constrained answers.
- **Teacher failure amplification.** Harder prompts mean the teacher is more often wrong. Without a correctness check, error rates rise round over round.
- **Style homogenization.** Because one teacher generates all mutations *and* all responses, both instruction and response style compress toward the teacher's mode. This is the "GPT-4-flavored" quality of many open synthetic datasets.

## Quality filters for synthetic data

Filters that consistently pay for themselves on synthetic outputs:

### Response-side filters

- **Language ID on the response.** Teacher accidentally answering in the wrong language happens more often than you would expect on non-English pipelines.
- **Refusal detection.** If your teacher refuses a prompt, both the prompt and the refusal are potentially useful (as a safety training signal — mod-106) *or* they are noise. Route them to a separate pile with a `refusal: true` metadata flag rather than letting them contaminate the general pool.
- **Length checks.** Too-short responses (single-sentence answers where the prompt clearly asked for detail) usually indicate a bad generation. Too-long responses (thousands of tokens for a one-liner prompt) usually indicate a hallucinated task expansion.
- **Format compliance.** Ran through the same format checks as chapter 1 (JSON validity, code-block presence when required, etc.).
- **Correctness — cheap version.** For code prompts: does the generated code parse? For math: does the final answer follow the "####" or `\boxed{...}` convention? Cheap syntactic checks catch the low-hanging errors.
- **Correctness — expensive version.** For code with test cases: run the tests in a sandbox. For math with ground truth: check the numeric answer. For reasoning: LLM-as-judge grading (with a separate stronger model to avoid the judge = generator conflict).

### Instruction-side filters

- **ROUGE-L / MinHash dedup against the growing pool** (from Self-Instruct; keep it).
- **Decontamination against MMLU / HumanEval / GSM8K / MT-Bench** (chapter 3). Synthetic pipelines *especially* need this — a teacher told to "generate a challenging math question" will happily reach for GSM8K style verbatim.
- **Judge-model instruction quality score.** Cheap when done on a batch; a 1–5 instruction quality rating from a smaller judge routes clear duds out of the pool.

### The provenance record

Every synthetic row must carry, at minimum:

```jsonc
{
  "generator": "gpt-4-turbo-2024-04-09",       // teacher model, versioned
  "generator_prompt_hash": "sha256:…",         // hash of the generation prompt
  "generator_temperature": 0.7,
  "generator_seed_ids": ["seed-042", "seed-118"],
  "evol_history": [                             // for Evol-Instruct
    {"operator": "add_constraint", "prior_id": "gen-000123", "round": 1},
    {"operator": "deepen",         "prior_id": "gen-000817", "round": 2}
  ],
  "filters_passed": ["language", "refusal_ok", "length", "format", "code_parses"],
  "judge_score": 4.2,
  "license_of_generator_output": "OpenAI-Terms-of-Use"   // see chapter 7
}
```

Without this record, "we generated some data with GPT-4" cannot become a defensible model card entry.

## The licensing question you must answer first

The single most consequential decision in a synthetic pipeline is *which teacher*. That decision is largely a licensing decision:

- **OpenAI models (GPT-3.5, GPT-4, o-series).** OpenAI's terms of service historically prohibited using outputs to train competing models. Interpretation and enforcement have shifted over time; consult the current terms and — for a shipped model — get legal review. - **Anthropic models (Claude 3+).** Similar language in Anthropic's terms. Same disclaimer. <!-- needs-research: confirm the current Anthropic Commercial Terms clause on training-on-outputs, with URL and date -->
- **Open teachers (Llama 3.1 405B, Qwen 2.5 72B, DeepSeek, Mistral Large, Nemotron).** License varies by model. Meta's Llama 3 community license explicitly permits training and even encourages "Llama"-named derivatives; Qwen and DeepSeek have their own licenses; some open teachers have permissive Apache 2.0 or MIT terms on outputs. **NVIDIA's Nemotron-4 340B** was released explicitly to be a synthetic-data teacher with a permissive license for that use.

The pattern to adopt: **before you generate a single token from a teacher, write down the license under which its outputs may be used to train and redistribute a model.** Put that string into the provenance record. Chapter 7's model card cannot exist without it.

## Alternative structures worth knowing

Self-Instruct and Evol-Instruct are two points in a wider space. Related pipelines you will encounter in the literature and on the Hub:

- **Alpaca** (Taori et al., 2023) — the reference Self-Instruct run against `text-davinci-003`.
- **Vicuna / ShareGPT-derived** — human-in-the-loop: real user conversations with a commercial assistant, filtered and reformatted. Provenance is messier; licensing is the persistent question.
- **UltraChat** (Ding et al., 2023) — multi-turn synthetic conversations across three-way topic taxonomy; ~1.5M dialogs generated from GPT-3.5.
- **OpenHermes / SlimOrca** (Teknium, Mukherjee et al., 2023) — recipes emphasizing curation and re-use of prior synthetic sets rather than fresh generation.
- **Distilling Step-by-Step** / **Orca** (Mukherjee et al., 2023) — teach a smaller model by generating rationales, not just answers, from a large teacher. Response quality much higher; teacher cost much higher too.
- **Self-Alignment / Self-Rewarding** (Sun et al., 2023; Yuan et al., 2024) — generate, self-critique, refine. Reduces teacher dependence but adds a new failure mode where the model reinforces its own errors.

Read at least one of these end to end — the paper *and* the dataset card — before you design your own pipeline.

## Summary

- Synthetic data lowers cost and unlocks scale, at the price of inheriting the teacher's biases, formatting tics, and license.
- **Self-Instruct** (Wang et al., 2023): seed pool → generate → classify → generate instances → filter (ROUGE-L, heuristics) → dedup → grow.
- **Evol-Instruct** (Xu et al., 2023): mutate existing instructions with depth (constraints, deepen, concretize) or breadth (topic shift) operators, re-generate responses, iterate rounds.
- Quality filters split into instruction-side (ROUGE-L dedup, decontam, judge-model score) and response-side (language, refusal handling, length, format, cheap and expensive correctness).
- Every synthetic row carries a provenance record: teacher name+version, generation prompt hash, temperature, evolution history, filter list, judge score, license.
- Resolve the teacher-license question *before* generation. Write the SPDX (or "vendor terms") string into provenance. Without it, chapter 7's model card cannot be written honestly.
